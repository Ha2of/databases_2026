3. Исследование work_mem

При 64 kB получил external merge и два параллельных работника. Основной процесс использовал 16 224 kB на диске, работники — 15 416 и 15 448 kB. Время составило 956,163 мс, временных блоков прочитано 23 488, записано 25 790.

При 256 MB сортировка перешла на quicksort, заняла 190 505 kB памяти и выполнилась за 921,765 мс. Временные файлы исчезли, ускорение составило около 3,6%. При этом план стал последовательным, поэтому результат зависит и от изменения параллелизма.

shared_buffers хранит страницы таблиц, а work_mem выделяется для сортировки и других операций. Поэтому даже при наличии таблицы в кеше промежуточные данные сортировки могут записываться во временные файлы. Затем эти части читаются при слиянии. Лимит work_mem относится к отдельной операции, а не ко всему серверу.

4. Сравнение индексов

На 100 000 строк B-Tree занял 2 208 kB, BRIN — 24 kB, то есть в 92 раза меньше. Перед итоговым замером убрал повторно вставленные строки и перестроил индексы.

BRIN хранит сводные значения для диапазонов страниц, а B-Tree — отдельные ключи со ссылками на строки. Для точечного OLTP-поиска по ID подходит B-Tree. BRIN полезен для диапазонов логов, когда значения связаны с физическим порядком строк.

Меньший fillfactor оставляет место для вставок и может отложить разделение страниц B-Tree, но увеличивает индекс. Партиционирование логов по времени позволяет исключать ненужные секции при запросах и проще удалять старые данные.

7. Системные объекты статистики

pg_stat_user_tables — представление в pg_catalog со статистикой пользовательских таблиц. last_analyze и last_autoanalyze содержат время ручного и автоматического анализа. n_mod_since_analyze оценивает изменения после анализа, n_live_tup и n_dead_tup — количество живых и мёртвых версий строк. seq_scan и idx_scan — накопленные числа сканирований. Использовал его для проверки flights и ticket_flights. Значения строк приблизительные и обновляются с задержкой; по одному NULL в last_analyze нельзя считать статистику устаревшей.

pg_stat_activity — представление в pg_catalog с текущей активностью. state показывает состояние сессии, wait_event_type и wait_event — категорию и событие ожидания. query содержит текущий или последний запрос, query_start — время его начала, backend_type — тип процесса. С его помощью проверял сессии и наблюдал ожидания сортировок и вставок. Это срез, а не история: короткое ожидание можно пропустить. Idle in transaction отличается от обычного idle наличием открытой транзакции.

pg_stat_statements — расширение с представлением в схеме установки. queryid определяет структуру запроса, calls считает исполнения, total_exec_time и mean_exec_time показывают суммарное и среднее время в миллисекундах. rows — суммарные полученные или затронутые строки, shared_blks_hit/read — попадания и чтения блоков, temp_blks_written — временные записи в блоках. Использовал для трёх рейтингов. Нужна предварительная загрузка библиотеки. Литералы нормализуются, повторные вызовы объединяются, статистика до включения не восстанавливается. Один запрос с разными настройками памяти может учитываться вместе.

pg_class — системный каталог в pg_catalog с описанием отношений. relname — имя, relkind — тип, relpages — оценка страниц, reltuples — оценка строк. pg_relation_size возвращает размер выбранной части отношения в байтах, pg_total_relation_size включает также индексы и TOAST таблицы. Через эти функции сравнивал B-Tree и BRIN. Оценки каталога могут устаревать, а размер индекса не показывает его скорость.

pg_prewarm — расширение и функция в схеме установки. Принимает отношение, режим, fork и начальный и конечный блоки. По умолчанию использует режим buffer и основную часть отношения. Buffer загружает данные в shared_buffers, read читает через ОС, prefetch запрашивает предварительное чтение. Возвращает число обработанных блоков. В моей работе прогрев уменьшил время JOIN. Загруженные страницы могут вытесняться, особенно если их больше вместимости кеша. Описание режимов: [документация](https://www.postgresql.org/docs/16/pgprewarm.html).

pgstattuple — расширение, pgstatindex — одна из его функций. Функции находятся в схеме установки. У pgstatindex index_size измеряется в байтах, leaf_pages — в страницах, avg_leaf_density и leaf_fragmentation — в процентах. У pgstattuple free_percent показывает долю свободного места. Использовал pgstatindex для сравнения fillfactor: плотность различалась, а итоговая фрагментация была почти одинаковой. Эти данные не дают точного числа page splits. Сканирование создаёт нагрузку, а конкурентные изменения могут влиять на результат. Описание полей: [документация](https://www.postgresql.org/docs/16/pgstattuple.html).

pg_stat_bgwriter — представление в pg_catalog с общей статистикой записи PostgreSQL 16. checkpoints_timed и checkpoints_req считают checkpoint по времени и по запросу. buffers_checkpoint, buffers_clean и buffers_backend считают записанные буферы для checkpoint, фонового писателя и клиентских процессов; buffers_alloc — выделенные буферы. Счётчики накоплены с момента stats_reset. Это помогает понять распределение записи, но не указывает конкретный медленный запрос. Для моего стенда такой просмотр дополнил бы исследование I/O; отдельный результат не фиксировал. Нагрузку следует оценивать по изменениям счётчиков за интервал.

pg_stat_database — представление в pg_catalog с общей статистикой базы. blks_hit и blks_read считают попадания и чтения блоков. tup_returned учитывает строки последовательных сканирований и записи индексных сканирований, tup_fetched — строки таблиц, извлечённые индексными сканированиями. xact_commit и xact_rollback — числа фиксаций и откатов. Это накопленные значения, начало периода показывает stats_reset. Представление подходит для общей проверки demo, но отдельного замера в работе не было. Оно не разделяет нагрузку по запросам, а число прочитанных строк не равно числу строк, отправленных клиенту. Описание общей статистики: [документация](https://www.postgresql.org/docs/16/monitoring-stats.html).

Полезнее всего оказались pg_stat_statements для поиска затратных запросов, pg_stat_activity для ожиданий и pg_stat_user_tables для проверки статистики. При следующей диагностике сначала проверил бы активность и свежесть статистики, затем планы основных запросов и временные записи. Изменения настроек сравнивал бы повторными замерами с учётом кеша и параллелизма.
